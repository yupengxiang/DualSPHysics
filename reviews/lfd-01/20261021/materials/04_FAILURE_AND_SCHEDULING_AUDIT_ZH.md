# 需要审阅的执行偏差

## 调度和汇报问题

1. 进度常以测试、版本、审查与提交汇报，五项最终产品长期为零却没有成为最前面的决策约束。
2. 从“读取一个实际输入”衍生出读数器、编译、ABI、权限、清单、夹具和发布协议的长链。每个局部修改有理由，但缺少整条关键路径的投资上限和明确退出决策。
3. 很多真实软件错误源于路径/版本/哈希混用、把未来产物要求成先验输入、夹具没有走真实接口、把 worker 与其子进程混同，以及覆盖/暂存路径不安全。通过合成检查后仍在真实任务接口失败。
4. 文档、状态和请求大量重复与追加，形成过期的“下一步”与当前事实并存。为了记录而扩张的控制层也增加了错误面。没有证明每个新层都阻塞一个必要科学验收。
5. 部分停止规则、观测前提和判据是主控自己引入的实现条件，应区分科学负结果与工程拒绝；反过来，也不能以发现工程问题为理由放松真实科学条件。

## 本轮主控自身的具体错误

- 初始 GenCase 头的 PeriMode=96 被错误地要求必须是 0。官方源码把 96 定义为 Unknown，初始加载器也显式使用 Unknown；这不是“已证实运行期非周期”，也不足以宣布物理案例失败。两次付费初态 guard 失败被原样保留，以独立来源证据作显式策略修订后才进行了新的事实观察。
- GenCase 工具实际返回 0 且产生资产，但外层日志后置条件失败。保留该父记录的 failed，仅建立真实资产来源与派生 preflight，未改写成完成收据。云端应审查这种来源续用的边界是否充分。
- 首次基线错误复用 S01 v14 对旧 NAS device83 的硬编码证明，被预启动拒绝。已存在且实际验证的 S01 v16 对 device53 有独立绑定，之后复用其既有方法、39 项实际软件验证和先前付费 probe；没有改写历史 BUILD004 证明或二进制哈希。
- 元数据准备器 v2 被主控错误地写成含字面转义的字符串。AST 语法检查仍可通过，但没有可执行 main。原文件及独立静态负评保留；真实源码 v3 才完成材料化。这是工程失误，不是科学失败。
- 新全帧调用器 v1 静态检查发现 MK 与 mkfluid 混用、错误终态状态假设、要求尚不存在的首次 hash 清单、最终发布覆盖风险，以及端点闭合与删失统计问题。v2 修了一部分，但又错误要求 request 含自身 SHA（不成立的自哈希依赖）。v2 未导入、未测试、未运行，不能称为可用链路；用户要求收尾后没有继续修复。

这些例子说明问题不只在上游数据，也在执行方式与主控集成质量。与此同时，真实的时序/质量/周期/身份和分辨率用途负结果依然成立或待定，不能被“工程问题”概括掉。需由云端分别决定保留哪些最低必要保护、哪些过度工程应删除、哪些案例应停止科学投入。

## 此次收尾边界

停止新增开发、审查扩张、求解、转换与测试；只等待已启动对照作业的正常有限终态，验证回收与唯一付费，冻结源码和未知项。母目标暂停且未完成。未执行 S/U/UF 控制，也没有为获得 pass 重复基线、裁时间窗、改观察区域或改数值阈值。下一步路线不由本地主控在本包中预先替云端决定。
