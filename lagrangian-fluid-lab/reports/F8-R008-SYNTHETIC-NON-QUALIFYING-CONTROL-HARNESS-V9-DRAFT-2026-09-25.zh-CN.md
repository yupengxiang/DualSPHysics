# F8 R008 synthetic non-qualifying control harness V9（规范性修订草案）

V9 以 V8 第 3、5 节的 parser/input/code 规则为基线；V9 明确替换 V8 第 1、2、4、6、7 节中与本文件不一致的 API、可信调度、consumer contract 与 gate 规则。未被替换的 V8 规则继续适用。V8 保留为历史版本。

状态：按 `gpt-5.6-terra` / high 配置请求的 V8 只读技术复核结论为 `REVISE`；当前工具未提供 reviewer model/effort 的独立 attestation，因此只记录技术意见，不声称可验证的 Terra High PASS。V9 吸收全部六项意见，并扩展 Core/F4 资格入口盘点。本文仍是设计草案：无 parser、consumer hardening 或测试实现；没有外部可信 launcher/root capability，故 production ingress 一律不可启用。F8 R008 execution gate 仍 open、`T1_numerical=false`、零信用。本草案不授权或启动 native decoder、GenCase、solver、worker、GPU 或 queue。

## 1. Synthetic-only API 与不可变返回

V8 第 1 节唯一 parser 的输入和验证顺序不变，但 API 返回改为精确的 15 项 primitive tuple，而不是 dict：

    diagnose_non_qualifying_synthetic_probe(raw_json_utf8, expected_scope_token,
                                             expected_qualification_row_token)
        -> DiagnosticTuple

`DiagnosticTuple` 是精确 builtin tuple；各索引按 V8 `OUTPUT_KEYS` 顺序对应 15 个字段。parser 可在函数内部构造临时 builtin dict，但构造后必须立即执行一次 validator：要求 `type(value) is dict`、`tuple(value.keys()) == OUTPUT_KEYS`、key/value 类型和值符合 V8 第 4/5 节；只从该 snapshot 构造 tuple。原 dict 永不返回、保存、传递或再次读取。调用端只能消费验证成功的 tuple。

V8 第 4 节所称 `OUTPUT_KEYS` 顺序因此成为可执行条件，不是序列化偏好。任何 validator/tuple 构造普通异常均转换为固定 `internal_error` tuple；若连该 tuple 也无法构造，则调用失败且无结果。V8 所述“result slot”不是 parser 的状态：同步 API 不持有 slot、cache 或跨调用结果。若外部系统以 timeout/cancel/异步 job 包装它，slot 由该 wrapper 按 invocation 唯一创建，初值为空，只能在校验本次返回 tuple 后写入；缺结果、超时、取消、异常或验证失败保持空，绝不复用旧值。

## 2. Production verifier 的可信 dispatch 与运行时边界

V8 第 2 节的调用方可传 verifier/version/scope/source-bindings 的 `accept(...)` 伪代码由本节替换。production 接口不接受调用方指定 verifier、root、scope、role list、source-binding tuple、allowlist 或 `consumer_id`。每个 consumer 有独立固定入口（例如 `accept_for_core_campaign(raw_bytes, trusted_context_capability)`）；入口将 consumer identity 闭包固定到可信 dispatch，不让外部 caller 选择较宽松的 consumer contract。各固定入口调用同一私有 helper；capability 必须绑定相同 consumer identity，否则拒绝。

    accept_for_consumer(raw_bytes, consumer_id, trusted_context_capability)

入口先从受信启动闭包提供的不可变 `CONSUMER_DISPATCH` 取合同，再验证 raw bytes。合同为精确、只读、不得由 JSON/CLI/调用者扩展的映射：

    consumer_id -> exact schema tuple ->
      (verifier_id, verifier_version, verifier_artifact_digest,
       exact verifier callable identity, trusted root-capability id,
       exact role-contract digest, expected-scope capability policy)

启动闭包必须验证 dispatch 本身、实际加载 verifier artifact 的原始字节 digest、callable 到 artifact 的归属，以及 root capability 身份；digest 对象也须与只读 root descriptor-relative/no-follow 读取的原始 bytes、role、byte count、scope 和 hash 一致。`trusted_context_capability` 只能由该启动闭包签发，不能由被验证 receipt 或 consumer 调用者构造。缺失/不匹配/能力不可证明时 fail closed。每个 schema/version 的 verifier 只按 dispatch 中预置函数调用，不用名称动态 import 或 service locator。

此前草案表中的 Python 文件 SHA-256 仅为代码盘点时的 review anchor，不是运行时 module identity、签名、builder 或 loaded-code attestation；不得据此声称源码到运行时闭合。运行时 digest 必须由可信启动闭包独立验证并绑定到 callable。这里的 root capability 指 out-of-band trust key 与受限 descriptor-root 能力，不要求也不暗示操作系统 root/sudo。当前环境没有该可信启动闭包/root-capability，因此上述 dispatch 不存在可启用配置；即使纯 Python parser 实现通过测试，production `accept_for_consumer` 仍须整体禁用。

成功验证仅返回该 consumer 专属的不可变、schema-specific capability，例如 `VerifiedCoreQualificationV1`、`VerifiedAdmissionV1`、`VerifiedF8StageB/C/D` 或 `VerifiedF8GateCell`；不得返回 dict、Mapping、通用可变对象或可序列化 capability。consumer 只能经固定字段 accessor 读取合同中列明的 primitive；跨进程/持久化/re-entry 必须从原始 bytes 重新验证。私有 Python 名称/类不能对抗同进程任意恶意代码，故仍依赖上述受信启动闭包；闭包不成立即 fail closed。

## 4. 两阶段 gate（无实现死锁）

**允许开始最小实现前**只要求：V9 设计复核通过；上述静态 consumer sweep 有范围/结果记录；每个已知入口具备唯一 test node ID、攻击 corpus、预期前置拒绝点与唯一 post-validation capability 类型；测试计划本身完成复核。此阶段不要求测试节点已经存在、执行或通过，否则会形成“测试先通过才能写测试”的死锁。设计审查不声称 machine-test pass。

**设计 gate 通过后可实现的范围**：纯内存 V9 parser/tuple validator、合成输入测试、以及为实现表中 fail-closed predicate 所必需的最小 raw-byte consumer ingress/verifier/拒绝 guard 和负向测试。不得修改、重生成、覆盖或重试已消耗的一次性 F3 row30/F4 supportcap 授权、授权回执或历史 namespace；需要保护这些路径时，只能另增兼容的版本化 wrapper，且不得改变其历史 hash/语义。不可连接 synthetic 输出到 production gate，不可写 registry/ledger/qualification evidence，不可因评审通过自动运行 solver、worker、GPU、queue 或 native tools。

**实现后、任何输出被 consumer 使用/持久化/接入前**：所有表内 node 必须存在并实际运行通过；覆盖 V8 第 3/5 节所有 parser/error precedence、exact 15-key output and tuple-order/type/code constraints、每个 consumer 的 exact Diagnostic/重标/包装/复制/重序列化/stale cache corpus；记录 node ID、pytest 结果、源码和 trusted-launcher manifest digest。任一项缺失、未运行或失败，consumer gate 为 FAIL。由于当前可信启动闭包/root capability 缺失，即使测试全过也不得启用 production acceptance 或给资格信用。

## 5. 明确保留的非目标

V9 及其 review/test 不证明 C-v1 solver execution、native integrity、T1/readiness 或任何机制家族资格；不调整冻结输入、阈值、失败分母或既有证据。V8/V9 review、合成测试和 `synthetic_bindings_match` 都不是生产 evidence。solver/native/GenCase/worker/GPU/queue 仍需各自独立执行门与授权。本文的 root capability 不是 sudo/root 权限请求。
