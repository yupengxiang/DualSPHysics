# F8 R008 C 阶段 execution-evidence synthetic schema v4（草案）

V4 继承 C-execution v3 的 synthetic-only 对象图、签名/编码、引用解析、diagnostic 输出与 trust boundary；仅替换控制时间窗与进程身份/生命周期的精确语义，并列出后续验证节点。它不是 production execution schema，不打开 gate，不给 qualification credit。未实现 parser、未运行测试；未启动 solver/native/GenCase/worker/GPU/queue。

这是独立新版本：envelope 与 `payload_schema` 固定为 `core.cfd.f8.r008_c_execution_evidence.synthetic.v4`；签名 domain separator 固定为 `ASCII("F8-R008-C-EXEC-SYNTHETIC-V4\n")`。V3 identifier、V3 signature prefix 或旧 payload 不得隐式升版、降版或作为 V4 输入；V4 synthetic parser 只识别自身精确 schema/version。V3 旧结构除本文件明示替换/增补字段外继续沿用，所有 JSON object 仍 `additionalProperties=false`。

## 1. 修正 v3 的全局时间上界

V3 §5 的单一条件 `effective_TimeMax <= min(T_end, control_table_end)` 删除。仅比较全局 `TimeMax` 与表末时刻既可能过度约束（最后一次实际查询后 simulation 才结束），也不能证明 query journal 完整或不存在 table extrapolation。

只读 source audit 已确认的参考调用链（实现时仍须重新绑定最终 source/build/feature closure）：

- `JDsAccInput::ReadXml` 对每个 active `<accinput>` 使用 `time.start=0`、`time.end=DBL_MAX` 默认；一个 MK range 可展开为多个 `Inputs` entry。每 entry 独立拥有 inclusive active window `[TimeIni_i,TimeEnd_i]` 和对应 acctimes table。
- CPU/GPU `PreInteraction_Forces` 分别调用 `RunCpu(TimeStep,...)` / `RunGpu(TimeStep,...)`。每个 `Run*` 对每个 entry 调 `GetAccValues(entry, TimeStep)`；inactive entry 不查询 table。若 active，acceleration 与 velocity table 按该 entry 的实际 double timestamp 求值。
- Verlet 每 step 查询一次；Symplectic predictor/corrector 可各查询一次但二者使用同一当前 `TimeStep`，并由 `LastTimestepInput` cache 命中；`TimeStep` 在 `ComputeStep()` 返回后才增加。VRes 走同一 host 力预处理路径。
- `JLinearValue` 在采样表首/末点外使用 endpoint-hold，不是数学外推；本 gate 仍要求实际 active query 落在表闭区间内。

## 2. 每次实际 query 的 no-extrapolation predicate

将 v3 `control_horizon_audit` 中 `effective_time_max_ieee754_hex`、`control_table_end_ieee754_hex`、`strict_query_bound` 这类单一全局上界，替换为与 attempt nonce、scope、qualification row、build/source closure 绑定的完整 `accinput_query_journal`。V4 evidence payload 在 V3 exact payload key set 上新增必需 `accinput_query_journal_binding`（stage=`runtime`, role=`accinput_query_journal`）；V4 reference-role allowlist 新增 `control_table`、`accinput_query_journal` 与 `source_callgraph`，并将 `(runtime,process_journal)` 的固定 consumer-registry target schema 设为 §3 的 V4 ID。`case_snapshot` 继续用于 XML/config raw object。V4 不扩展 V3 descriptor-ref shape：journal ref 与 audit 内副本均为 V3 exact 五字段 `{stage,role,object_id,bytes,sha256}`，每字段类型/domain 及 descriptor-relative resolution 继承 V3；两副本须逐字段完全相等。ref 不携带 `target_schema` 或 canonical digest；各 role 的 target schema 由固定 `(stage,role)` consumer registry 决定，journal 原始 bytes 由 ref 的 `bytes/sha256` 绑定。V4 `control_horizon_audit` exact keys 为 `{scope_digest,qualification_row_digest,source_callgraph_binding,accinput_query_journal_binding,entry_count,poll_count,all_active_queries_in_table_domain,zero_active_query,comparison_rule}`；`comparison_rule="binary64_numeric_strict_no_tolerance"`；旧全局 horizon/table-end 字段禁止出现。`scope_digest` 与 `qualification_row_digest` 必须分别逐字节等于 V3 payload `scope_binding.sha256` 与 `qualification_row_binding.sha256`（都是 descriptor ref 所指对象 raw bytes 的 SHA-256，不是 canonical JSON digest）；二者先按 V3 stage/role/object allowlist 验证。audit 值必须由验证器从已验证 journal 确定性派生，不采信 caller booleans。journal 的 `source_id` 必须等于 evidence payload `runtime_image_binding.object_id`，`source_binary_sha256` 必须等于该 ref 的 raw `sha256`；query journal 与 process journal 两项 identity 必须相同。process-generation 引用必须存在于同一 attempt 的 V4 process journal；不存在、overflow、丢事件或 call graph 未绑定均只能给 `open`。

Query journal exact top-level keys 为 `{schema,attempt_nonce_hex,source_id,source_binary_sha256,coverage_start_ns_hex,coverage_end_ns_hex,event_count,overflow,lost_count,entries,loop_guards,polls}`；schema 固定 `core.cfd.f8.r008_c_execution_accinput_query_journal.synthetic.v4`，nonce 必须等于 evidence payload `nonce_hex`，`source_id` 必须等于其 `runtime_image_binding.object_id`、`source_binary_sha256` 必须等于该 ref 的 raw `sha256`；相同两项也必须与 V4 process journal 完全相等。`overflow=false`、`lost_count=0`；`len(entries) <= 65536`、`event_count <= 100000000`、raw journal bytes `<= 1073741824`。全局 event sequence 覆盖 `loop_guards ∪ polls`，严格为 `0..event_count-1`，`event_count == len(loop_guards)+len(polls)`。

`{stage,role,object_id,bytes,sha256}`。固定 `(build,source_callgraph)` registry target schema 为 `core.cfd.f8.r008_c_execution_source_callgraph.synthetic.v4`。被引对象 JSON 顶层 exact keys 为 `source_fragments` 的每个 `source_file_object_id` 必须按上表映射到 build attestation 所绑定 source manifest 的一个且仅一个 regular-file ref；byte offsets/ordinals 是 bool-forbidden、有界 JSON integer。`ordered_call_edges` 只列实际 build flags 下 preprocessed translation unit 中存活的边，所以 `active_preprocessor_condition` 固定为 builtin string `"active"`；被裁去的 branch 不入数组，未识别的 feature macro 令 gate open。source-function/call-edge arrays 的成员和排序都由 extractor 重算，JSON 自报内容只作 comparison target。

R008 runtime identity 也由 extractor 唯一派生：standard driver 为 `driver_id="main"` 且唯一 instance 为 `solver_instance_id="main"`；VRes driver 为 `driver_id="vres"`，每个 `VResObj` 按零基 vector position `i` 命名为 `solver_instance_id="vres.%02u"`（printf 最小两位宽，超 99 后自然扩位，范围 `0..65535`），且 `solver_instance_ids` 数组按该 vector 顺序排列。任何其他 driver/instance ID 即拒绝；entries、source callgraph 与 polls 必须逐 ID 一致。

关键安全约束：source-callgraph JSON 只是受 raw hash 绑定的声明，不能自证其 `drivers/instances/source_fragments` 内容。V4 verifier 必须从 payload 已验证的 build attestation/source manifest、runtime image、invocation、configuration/external-config/case snapshot refs，使用 verifier 内固定的 `f8-r008-source-callgraph-extractor-v1` 重新解析源码与运行配置，重新导出 source ranges、AST/call edges、driver/instance order 与 host-call schedule，并要求 canonical projection 完全相等；不可将对象中自报拓扑直接转为 capability。extractor 按实际 build flags/feature set 预处理并解析上述固定 function allowlist，逐 definition 复算 byte range、raw fragment SHA、完整 function-definition AST 的 RFC 8785 canonical digest 与 source-order call edges；对 indirect/virtual dispatch 必须有受信 points-to resolution，否则拒绝。runtime projection 由同一受信 parser 重读 exact argv/env、generated XML、external case/VRes configuration 与已绑定 input/MK inventory，独立重建 active solver instance 列表及展开后 `JDsAccInput::Inputs`，再与 callgraph `drivers/instances` 及 journal `entries` 完全相等。该 extractor 的 parser implementation 及 revision 必须包含于 out-of-band 激活所 pin 的 `verifier_sha256`；仅声明 extractor ID/hash 不构成信任。若编译器前端/flags/feature closure不匹配、无法无歧义解析运行配置或 topology、源码定义/AST/call edge 摘要不相等、出现未知间接边，均 `open`。V3 activation 不可激活 V4；当前没有此 root-owned extractor/verified build-runtime closure，因此即使 synthetic object 结构有效也恒为 `gate_state="open"`、零信用。

每个 true guard 必须且只能产生由 driver 的有序 instance 列表、各 instance 的有序 intersteps、升序 `input_index` 展开的完整 poll 序列；每个 poll 的 callsite/integrator/interstep/input 与重解析结果逐项相等。false guard 不产生 poll。这样 expected host-call × entry 覆盖必须由源代码 AST 与已绑定运行配置重新推导，而非由 producer 的布尔声明或 JSON 自报 callgraph 自证。

`entries` 按 `(solver_instance_id,input_index)` 严格升序，每个展开后的 input 恰有一条 definition，字段恰为：`solver_instance_id`, `driver_id`, `input_index`, `xml_element_ordinal`, `range_segment_ordinal`, `enabled`, `time_ini_ieee754_hex`, `time_end_ieee754_hex`, `table_first_time_ieee754_hex`, `table_last_time_ieee754_hex`, `table_raw_binding`, `entry_definition_sha256`。`solver_instance_id` 为固定 ASCII ID `[a-z0-9][a-z0-9._-]{0,63}`，由 source-bound runtime 对每个独立 `JDsAccInput` 实例分配唯一固定 ID；标准单实例为 `main`，VRes/多域配置为各实例登记 ID。`driver_id` 使用相同 ASCII grammar；source-bound call graph 必须将每个 solver instance 恰好映射到一个 driver，并声明该 driver 的 loop guards 覆盖哪些实例（VRes driver 的单一外层 loop 覆盖其全部 `VResObj`）。所有 index/ordinal/byte offset/seq 均为有界 JSON integer（bool 禁止）；`enabled` 为精确 bool `true`；hash 为 64 位 lowercase hex；每个 `*_ieee754_hex` 为 IEEE-754 binary64 位型的 16 位 lowercase hex。`input_index` 与该实例最终二进制构造的 `JDsAccInput::Inputs` 零基位置一致；未激活 XML 节点不得伪装成 runtime entry。`entry_definition_sha256` 是去掉该字段后按固定 canonical JSON 规则序列化 entry 的 SHA-256。`table_raw_binding` 是以下 discriminated union 之一：

- file table：exact `{kind,table_ref}`，`kind="external_file"`，`table_ref` 为 V3/V4 descriptor-relative ref，stage=`runtime`、role=`control_table`，解析基准固定为同一 case `DirData` root FD，不接受 host path 或 symlink。
- inline `<acctimes>`：exact `{kind,document_ref,accinput_element_ordinal,acctimes_element_ordinal,byte_start,byte_end,slice_raw_sha256,parsed_samples_canonical_sha256,xml_parser_id,xml_parser_sha256}`，`kind="inline_xml_slice"`；`document_ref` stage=`runtime`, role=`case_snapshot` 并绑定完整 XML raw bytes；offset 为该 bytes 中从 0 起的半开区间 `[byte_start,byte_end)` 且 `byte_end>byte_start`；`slice_raw_sha256` 必须等于原始 byte slice 的 SHA-256，parser/source slice 必须指向同一 XML tree 中相应 accinput/acctimes ordinal。XML 固定 strict UTF-8、拒绝 BOM、DTD 与 external entity；解析后的 sample rows 按原顺序将每个 double 编为 16-char IEEE-754 hex，再对 canonical JSON 数组求 `parsed_samples_canonical_sha256`。`xml_parser_id` 为固定 ASCII ID，`xml_parser_sha256` 为 64 位 lowercase hex。若受信 parser 无法给出可验证的原始 byte offsets、或 source/build closure 未绑定 parser，则 inline table 保持 `open`，不得退化为只 hash parsed samples。

两种 binding 均包含并验证原始 input object 的 bytes/hash/mount identity；file table 的 `object_id` 必须等于从同一已绑定 XML 的 `<acctimesfile value>` 按冻结 `DirData` 相对解析所得的 allowlisted object，inline table 的 slice 必须恰是对应 `<acctimes>` 的完整 source bytes；`table_first_time`/`table_last_time` 必须由这些同一 raw bytes 按 bound parser 重算。定义缺失、重复、无法从 XML/range/feature parser 唯一重建，或 table 来源未绑定，均为 `open`。

`loop_guards` 的 exact event keys 为 `{seq,process_generation_id,driver_id,loop_iteration_id,time_step_ieee754_hex,time_max_ieee754_hex,condition_result}`；`driver_id` 同上，`loop_iteration_id` 为非负、有界 JSON integer；每个实际进入的 driver 外层时间循环 guard 恰有一个 event，`condition_result` 精确等于该时刻 `TimeStep < TimeMax`，只有 true event 可以被 poll 引用。VRes 的 `RunVRes()` 在单一 driver-level `while` 内依序运行多个 `VResObj`，因此同一 guard 合法地服务于该 driver 映射的多个 solver instance；不得为每个 instance 伪造/复制 guard。`polls` 的 exact event keys 为 `seq,process_generation_id,solver_instance_id,driver_id,loop_guard_seq,callsite_id,integrator,interstep,input_index,timestep_ieee754_hex,active,cache_status,sample_provenance`。`loop_guard_seq` 必须引用同一 process generation 与 `driver_id` 的 guard；poll 的 `driver_id` 必须与 entry 和 source-bound instance→driver map 一致；poll timestamp 必须 bit-exact 等于 driver guard 的 `time_step`，且 guard `condition_result=true`。所有 `seq`/index 为有界 JSON integer（bool 禁止），solver/driver IDs 满足相同 ASCII grammar，time 字段均为 fixed 16-char IEEE-754 hex；callsite ID 仅允许精确字符串 `cpu.pre_interaction_forces.run_cpu` 或 `gpu.pre_interaction_forces.run_gpu`；`integrator` 仅 `{Verlet,Symplectic,VRes}`；`interstep` 仅 `{INTERSTEP_Verlet,INTERSTEP_SymPredictor,INTERSTEP_SymCorrector}`；`cache_status` 仅 `{miss,hit}`。inactive poll 的 `sample_provenance=null`；active cache-miss 的 `sample_provenance` exact object 为 `{table_raw_binding,source_poll_seq}` 且 `source_poll_seq==seq`，其 `table_raw_binding` 必须逐字段完全等于本 poll `(solver_instance_id,input_index)` 对应 entry 的绑定。active cache-hit 的同形 object 必须指向同 process generation、同 solver instance、同 input、同 bit-exact timestep 的既有 miss poll，且其 `table_raw_binding` 必须同时等于对应 entry 绑定与来源 miss poll 的绑定。它表示实际返回样本的来源，不声称 cache hit 时重新读取/插值表。每个 poll 的 `(solver_instance_id,input_index)` 必须存在于 entries。每一个 expected host call × 每个实例内 input entry 必须恰有一个 poll，不得通过只记录 active 查询隐藏 inactive polls；driver→instance topology 与所有预期调用数须由 source/build-bound call graph 确定。

`active` 必须精确等于 `enabled && TimeIni_i <= t_query && t_query <= TimeEnd_i`。Symplectic 同时间第二次 poll 必须反映实际 cache hit；缓存必须引用同一进程 generation、solver instance、entry 与二进制时间戳上的先前 cache-miss poll，不得伪造新插值或省略这次 host call。

`control_horizon_audit.entry_count == len(entries)`、`poll_count == len(polls)`；`all_active_queries_in_table_domain` 与 `zero_active_query` 是验证器重算的 exact bool，后者等于不存在 active poll。零 active 时前者只能表示空集上的逻辑真值，不能代表控制资格或 credit。

对**每一个实际 active event**，必须同时满足无容差 binary64 数值比较：

1. loop guard：`t_query < TimeMax_at_loop_guard`，其中 `TimeMax_at_loop_guard` 从 poll 所引用的 loop-guard event 读取；guard 值必须来自同一时刻的受信 event，而非 poll 自述、最终配置或日志推测。
2. per-entry active window：`TimeIni_i <= t_query <= TimeEnd_i`。
3. per-entry table domain：`table_first_i <= t_query <= table_last_i`，首尾等值允许；任一超界、NaN/Infinity、转换或时间比较不一致均 `open`。

不要求 `TimeMax` 本身小于 table endpoint，也不把未执行的最后半步当成一次查询。动态 `TimeMax`、CLI/OPT overlay、TERMINATE、minimum-fluid 与 `NstepsBreak` 仍要由同一 attempt journal 解释；完整 query set 必须能与每次 ComputeStep/host force entry 建立一一对应的完整性证明。空 journal、零 active query 或所有 entry inactive 仅可得 `control_input_not_demonstrated`、`qualification_credit=0`、`gate_state="open"`，不得以“无越界事件”声称实际驱动成功。

建议未来 synthetic-only negative nodes：

- `test_c_execution_synthetic.py::test_query_domain_is_checked_per_entry_without_global_horizon_shortcut`
- `test_c_execution_synthetic.py::test_table_endpoints_are_inclusive_and_any_outside_query_opens_gate`
- `test_c_execution_synthetic.py::test_empty_or_inactive_query_journal_has_zero_control_credit`
- `test_c_execution_synthetic.py::test_query_journal_must_cover_every_cpu_gpu_call_and_symplectic_cache_hit`
- `test_c_execution_synthetic.py::test_source_callgraph_ref_and_runtime_build_closure_are_exact`
- `test_c_execution_synthetic.py::test_source_callgraph_projection_must_match_reparsed_ast_and_runtime_instances`
- `test_c_execution_synthetic.py::test_scope_and_qualification_digest_mismatch_keeps_gate_open`

## 3. 进程身份、PID 重用与 supervisor 隔离

V4 payload 中 `process_journal_binding` 保持 V3 exact 五字段 ref shape，role 固定 `process_journal`；固定 `(runtime,process_journal)` consumer-registry entry 必须解析为 `core.cfd.f8.r008_c_execution_process_journal.synthetic.v4`。V3 process-journal payload schema/event union 不可作为 V4 journal。process journal 顶层 exact keys 为 `{schema,attempt_nonce_hex,source_id,source_binary_sha256,coverage_start_ns_hex,coverage_end_ns_hex,event_count,overflow,lost_count,events}`；`lost_count` 是非负 JSON integer 且必须为 0；其余 key/type/size limits 沿用 V3；`schema` 固定上述 v4 ID，`events` 改用本节 exact union。相同 ref shape 只说明 raw object 定位格式相同，不能使 V3 payload/event 被当作 V4。

V3 process journal 的 `pid` 不足以在进程退出、fork 或 PID reuse 后唯一指认执行实体。V4 每个 process instance 固定身份：

`process_generation_id` 是 exact JSON object `{pid_namespace_inode_hex,pid,start_monotonic_ns_hex,kernel_starttime_ticks_hex,birth_seq_hex}`。namespace inode、monotonic timestamp、kernel starttime 与 birth sequence 均为 16-char lowercase hex；`pid` 为正 JSON integer，表示该 PID namespace 内 thread-group leader 的 TGID，不是任意 TID。`start_monotonic_ns_hex` 取执行前固定 `CLOCK_MONOTONIC` 读数；`kernel_starttime_ticks_hex` 取同一 boot 的 `/proc/<TGID>/stat` field 22（按 closing `)` 后的 proc-stat grammar 解析），并与固定 host boot ID、pid namespace inode 及稳定 pidfd/task handle 绑定；`birth_seq_hex` 等于创建该 process generation 的 `spawn/fork/clone_process` event `seq` 编为 16-char hex，因此唯一且不可复用。可信监测须使用稳定 task handle（如 pidfd）把 namespace/TGID/kernel starttime 与创建事件绑定；仅 supervisor 自报 monotonic timestamp 不足以证明唯一性。`thread_generation_id` 是 exact `{tid,start_monotonic_ns_hex,kernel_starttime_ticks_hex,birth_seq_hex}`；其 birth sequence 对应 `thread_create` event，thread start time 取 `/proc/<TID>/stat` field 22 并绑定所辖 process generation。普通 OpenMP/pthread 线程不伪装成独立 process generation。trusted launch/spawn、`fork` 或 `clone_process` 创建新 process generation；`exec` 仅记录同 generation 的 image replacement，不改变其 identity；process `exit` 与 `reap` 必须引用完整 generation ID。PID/TGID 仅在上一 generation 已 exit 且 reap 后才能复用；TID 仅在所属 thread generation 已 `thread_exit` 后才能复用。仅看到同数值 ID 的后续事件而缺失相应终止事件/new birth sequence 一律 `open`。

全 journal 事件 `seq` 必须从 0 连续递增至 `event_count-1`、无重复/跳号；单调时间非递减；`overflow=false` 且 producer `lost_count=0`。V4 process-event union 必须精确为：`spawn={seq,mono_ns_hex,kind,process_generation_id,supervisor_identity_binding}`（solver root only）；`fork={seq,mono_ns_hex,kind,parent_generation_id,process_generation_id}`；`clone_process={seq,mono_ns_hex,kind,parent_generation_id,process_generation_id,clone_flags_hex}`；`thread_create={seq,mono_ns_hex,kind,process_generation_id,thread_generation_id,clone_flags_hex}`；`thread_exit={seq,mono_ns_hex,kind,process_generation_id,thread_generation_id}`；`exec={seq,mono_ns_hex,kind,process_generation_id,executable_binding,argv_sha256,cwd_object_id,environment_sha256}`；`exit={seq,mono_ns_hex,kind,process_generation_id,exit_code,signal}`；`reap={seq,mono_ns_hex,kind,process_generation_id}`；`load={seq,mono_ns_hex,kind,process_generation_id,object_binding,object_kind}`；`cgroup={seq,mono_ns_hex,kind,process_generation_id,action,cgroup_id}`。每个 branch 只允许列出的字段。`clone_flags_hex` 是 16-char lowercase hex Linux clone-flags 位图；`clone_process` 必须清除 `CLONE_THREAD` 并创建不同 TGID，`thread_create` 必须设置 `CLONE_THREAD` 且新 TID 的 TGID 等于所绑定 process generation 的 TGID；可信 kernel event source 必须分类记录所有 clone，未知/不一致 flags、未分类 task 或事件丢失均 `open`。`birth_seq_hex` 对 process generation 必须等于其 `spawn/fork/clone_process` event `seq` 的 16-char lowercase hex 编码，对 thread generation 必须等于 `thread_create` event `seq`。root spawn 不含 parent；fork/clone_process 的 parent generation 必须当前为 running。每个 `thread_create` 必须在所属 process `exit` 前恰有一个匹配 `thread_exit`；thread TID 只能在此前 exit 后复用新 birth sequence；线程不产生 process `reap`。process exit 仅允许 `(exit_code integer,signal=null)` 或 `(exit_code=null,signal positive integer)`；process reap 只能发生在其 exit 之后。验证器按 `created → running → exited → reaped` 状态机核对 process parent/child generation graph；fork/clone_process 后 child 直接运行时不要求 exec，但只允许在有效 generation 上出现 exec/load/cgroup/exit/reap。所有 process generation 均须从唯一 solver root 可达并最终 exit/reap；线程及其代码加载/cgroup membership 均归属对应 process generation，线程不得迁移到 solver cgroup 外，或迁移事件必须被完整记录并 fail-closed。引用不存在、状态不匹配、线程退出缺失或 task 未分类均 fail-closed。solver root generation 必须绑定可信 spawn/launch event。监督进程须处于 solver cgroup 外且身份由独立 trust/build closure 固定；不能由 solver 自签 journal 证明 supervisor 身份或完整事件覆盖。

新增 synthetic negative node 提案：`test_c_execution_synthetic.py::test_pid_reuse_requires_prior_reap_and_new_process_generation` 与 `test_c_execution_synthetic.py::test_missing_child_reap_or_same_cgroup_supervisor_keeps_gate_open`。当前均不存在；pass 也不证明实际 supervisor producer 可信。

## 4. 输入对象引用继续采用 descriptor-relative raw binding

输入 table、XML/config、OPT、restart 与 case snapshot 必须通过 V3 stage/role/object-id reference，在各自固定 root directory FD 内 no-follow 打开；对每对象绑定 raw byte size/SHA-256、regular-file 类型、single-link 约束与 mount identity。禁止 `resolve()` 后按 host path 再开、跟随 symlink、跨 mount 替换，或只绑定 parsed/canonical JSON 而忽略实际 input bytes。query journal 中每个 `table_raw_binding` 必须与此快照同一对象身份及摘要完全相等。

## 5. 明确仍未闭合的 production blockers

本版不定义或实现下列信任事实，故全部仍 BLOCKED、execution gate 始终 open：

- 独立 trusted supervisor 及完整、不可漏报的 process/input/query/termination/resource event source；
- 执行前 out-of-band trust activation、撤销与 key 生命周期；
- 最终源码树、编译宏/feature 集、builder、产物、动态库/CPU/GPU device image 到已加载 binary 的闭合证明；
- exact cgroup v2 resource event/limit schema 与读取者身份；
- GPU multi-device/多进程 terminate 传播，以及 `TerminateTimeMax` 最终读取/生效语义；
- R008 最终 runtime/OPT/config/input snapshot、控制 query producer 和完整资格运行终态。

C-v1 永不因 `solver_execution={}` 或 C-v1 `passed` 而映射到 execution gate。V4 只供将来 synthetic-only parser/schema negative tests 使用；不改 C-v1，不写 gate registry，不创建 production activation，不授权或运行 solver、worker、GPU、queue、native 或 GenCase。
