# F8 R008 Terminal Completion Evidence Contract v6

**Status:** additive proposal only; diagnostic-only; no solver/execution/readiness/qualification authority. Effective contract is v3 plus v4 plus v5 plus this amendment. V1–V5 and their review records remain immutable. Required trust service, Linux supervisor, audit monitor, locale monitor, and verifier are not currently deployed.

## 1. Freeze one external policy and one registry snapshot (replaces v5 §1 rollover semantics)

There is exactly one registry snapshot for an R008 attempt. It cannot roll forward within the attempt. The task policy is installed outside the repository by the workflow owner and opened by the trusted verifier through a pre-opened descriptor; neither a path nor bytes may come from the receipt/candidate. The verifier's trusted configuration pins the policy-root public key.

Task policy is canonical UTF-8 JSON with exact keys:

~~~text
{schema,task_id,root_key_id,policy_sequence,issued_time_ns,
 not_before_ns,not_after_ns,genesis_anchor_sha256,
 registry_payload_sha256,registry_sequence,registry_key_id,time_key_id,
 dependency_pin_set_id,allowed_scope_ids,allowed_host_ids,signature_base64}
~~~

schema is core.cfd.f8.r008.task_policy.v1. The root key ID and 32-byte Ed25519 public key are pinned in trusted verifier configuration, not in this object. Policy is signed over ASCII("CORE-F8-R008-TASK-POLICY-V1") || 0x00 || canonical(policy without signature_base64). IDs use the v4 pattern; digests are 64 lowercase hex; time and sequence fields are exact positive JSON integers ≤2^63−1; scope/host arrays are nonempty, sorted and unique. The pre-opened policy bytes, descriptor identity, digest, root signature, validity, scope and host are verified before candidate files. Every policy object has additionalProperties=false.

The policy pins one genesis-anchor digest, one registry-payload digest, one registry sequence, registry/time key IDs, and one dependency-pin-set ID. Registry sequence and payload digest must equal these values exactly. The receipt's seventh trust_registry pin equals the fixed registry schema ID and payload digest. The registry contains only the six non-self-referential dependency records from v5. To revoke/rotate a key, the task owner must install a new root-signed policy and registry snapshot through the external administrative channel with an atomically increased monotone policy_sequence; an in-flight attempt never accepts a replacement. Before final verification, the trusted verifier confirms its external current policy sequence/digest is still the one frozen at prelaunch; change during execution makes that attempt missing/open. This administrative update channel is out of scope and may not be invoked by a candidate or receipt.

The registry's revoked-key list is authoritative for the fixed policy interval; trusted-time checks enforce policy/registry/key validity at prelaunch and final verification. The separate nonce-bound time attestation rules in v4 remain. Policy/registry validity fields are exact integers with not_before ≤ issued ≤ not_after, and the trusted unix_time_ns must fall inclusively in both validity intervals. If the policy, trusted root, snapshot, trusted time, or monotone policy state is absent, invalid, stale, rolled back, or changed mid-attempt, terminal evidence is missing/open.

## 2. Correct the post-exit watcher rule

The v5 termination_watch contains exactly one non-filesystem control event of kind seal after child exit. That one event is allowed and must match output_seal/evidence. All filesystem events after child exit—create, write, rename, unlink, attribute change, or close-write—are forbidden and reject. The seal control event has null paths and is not a filesystem mutation. No other event kind is permitted. Each event has exact fields {sequence,monotonic_ns,kind,path_before,path_after,actor_pid,actor_start_ticks}; sequence is contiguous, actor identity is exact, filesystem paths are output-root-relative, and the seal event has null paths and the verifier PID/start-ticks. This replaces v5's contradictory “any event after child exit” sentence.

## 3. Mechanically verifiable kernel seal evidence (replaces v5 §2 summary-only seal claims)

The v5 execution protocol remains fixed: fresh private mount namespace, private tmpfs output mount, single child writer cgroup, complete descendant reap, close supervisor write FDs, recursive Linux mount_setattr(MOUNT_ATTR_RDONLY|AT_RECURSIVE), and post-seal reads through held descriptors. V6 adds raw verifier observations and exact cross-links.

The top-level receipt required-key set is the complete v3 set plus output_seal, output_seal_evidence, sealed_tree_manifest, locale_attestation, and bi4_format_profile. Every added object is exact-keyed with additionalProperties=false. output_seal has exact keys:

~~~text
{schema,namespace_inode,mount_id,mount_major,mount_minor,root_dev,root_ino,
 writer_cgroup_inode,child_pid,child_start_ticks,process_group_id,watcher_id,
 verifier_nonce,seal_monotonic_ns,read_only,write_fd_count,
 sealed_tree_manifest_sha256,output_seal_evidence_sha256}
~~~

schema is core.cfd.f8.r008.output_seal.v1; read_only is exact true; write_fd_count is exact zero measured after child-cgroup empty and before mount_setattr; identities and unsigned fields use v3 bounds; times are 1..2^63−1; hashes are 64 lowercase hex; verifier_nonce is 32-byte lowercase hex. output_seal_evidence_sha256 is SHA-256 of the complete canonical output_seal_evidence JSON object including signature_base64. sealed_tree_manifest_sha256 is SHA-256 of the complete canonical sealed_tree_manifest JSON object. All values must equal independently observed fields in output_seal_evidence. The watcher_id must equal termination_watch.watcher_id and fanotify_profile.watcher_id.

output_seal_evidence has exact keys:

~~~text
{schema,verifier_id,verifier_key_id,nonce,observed_monotonic_ns,
 namespace_stat,mountinfo_before,mountinfo_after,cgroup_procs_before,
 cgroup_events_before,cgroup_procs_after,cgroup_events_after,
 task_snapshot_before,task_snapshot_after,namespace_fd_records,wait_statuses,
 fd_records_before,fd_records_after,mount_setattr_record,
 statx_after,statvfs_after,producer_byteorder_observation,
 fanotify_profile,fanotify_events,
 sealed_tree_manifest_sha256,signature_base64}
~~~

It is signed by the registry-pinned verifier key with role verifier over ASCII("CORE-F8-R008-OUTPUT-SEAL-EVIDENCE-V1") || 0x00 || canonical(evidence without signature_base64). verifier_id/key ID, nonce and monotonic time bind to the same trusted verifier invocation and output_seal. This signature authenticates raw observations; it does not make an unavailable or untrusted verifier authoritative.

Each field is a typed raw observation, not a caller boolean:

- namespace_stat is the verifier's fstat of its held /proc/self/ns/mnt descriptor: exact {dev,ino}; ino equals namespace_inode.
- mountinfo_before/after are exact {raw_base64,raw_sha256}; bytes are strict UTF-8, ≤1 MiB, no NUL, and decode to the kernel /proc/self/mountinfo contents. The profile parses each line using the Linux mountinfo grammar and identifies one exact mount ID/device/root/mountpoint. Before seal it is the expected private rw tmpfs; after seal it is the same mount, same device/root/mountpoint, private propagation, ro mount and superblock flags, with no unexpected submount.
- cgroup_procs_before/after and cgroup_events_before/after use the same exact {raw_base64,raw_sha256} type, each ≤1 MiB. The cgroup-v2 file bytes use ASCII LF records. After values must be exactly empty cgroup.procs and populated 0 in cgroup.events; the child and every descendant observed before exit have a successful wait/reap record.
- task_snapshot_before/after are sorted records {pid,start_ticks,mount_namespace_inode,cgroup_inode,state}; state is one exact Linux task-state character from the pinned proc profile; after contains only the verifier/supervisor and no child/descendant. The verifier scans every task visible in the host PID namespace and emits namespace_fd_records {pid,start_ticks,fd,namespace_inode} for every descriptor resolving to this mount namespace; only the verifier/supervisor may remain. No unregistered task or leaked namespace handle is allowed.
- wait_statuses are sorted unique {pid,start_ticks,waitid_code,waitid_status,exit_monotonic_ns}; one row exists for every child/descendant, start ticks match task_snapshot_before, and the primary solver row is a normal zero exit without signal/cancel.
- fd_records_before/after are sorted {pid,start_ticks,fd,fd_flags,mount_id,dev,ino,mode}. They are collected from /proc/<pid>/fd plus fdinfo for every task whose mount_namespace_inode matches; flags are the kernel open flags. Before mount_setattr, all child tasks are reaped, supervisor write FDs are closed, and there are zero descriptors whose mount_id is the output mount and whose access mode is O_WRONLY/O_RDWR. After sealing, the same count is zero. Any inaccessible /proc entry, PID reuse, or unclassified FD makes evidence missing/open.
- mount_setattr_record is exact {tid,start_ticks,dirfd_mount_id,flags,attr_set,result,errno,monotonic_ns}; flags is AT_RECURSIVE, attr_set is MOUNT_ATTR_RDONLY, result is 0, errno is 0, and the call occurs after cgroup empty/zero write FDs and before statx_after/statvfs_after. A pinned ptrace syscall-entry/exit monitor supplies the raw result.
- statx_after is {mount_id,dev_major,dev_minor,ino,mode}; statvfs_after is {flags,readonly}. Both are queried by the verifier through held descriptors after the remount; mount ID/device/inode match output_seal and readonly is exact true.
- producer_byteorder_observation is exact {monotonic_ns,source_module_sha256,getbyteorder_value,raw_probe_base64}; it is captured inside the identified child before first BI4 write. getbyteorder_value is the pinned source enum value 0 (LittleEndian); raw_probe_base64 decodes to exactly four bytes produced by interpreting uint32 value 1 in native memory and must equal 01 00 00 00. The source module hash is in the frozen solver source closure. This record independently binds the profile's little-endian constraint to the producing process; any mismatch leaves BI4 terminal proof missing/open.
- fanotify_profile has exact keys {schema,watcher_id,monitor_sha256,mount_id,mark_type,report_mode,event_mask,queue_limit,start_monotonic_ns,stop_monotonic_ns,overflow_count}; schema is core.cfd.f8.r008.fanotify_profile.v1, hashes are 64 lowercase hex, watcher_id equals output_seal.watcher_id, mark_type is FAN_MARK_MOUNT, report_mode is FAN_REPORT_PIDFD, and event_mask is the pinned bitwise union of FAN_CREATE|FAN_DELETE|FAN_DELETE_SELF|FAN_MOVE|FAN_MODIFY|FAN_CLOSE_WRITE|FAN_ATTRIB|FAN_OPEN_PERM|FAN_OPEN_EXEC_PERM with FAN_EVENT_ON_CHILD|FAN_ONDIR. queue_limit is exact integer 1..1,000,000 and overflow_count is zero. fanotify_events are sequence-ordered actor-aware events {sequence,monotonic_ns,mask,pid,pid_start_ticks,path_before,path_after}; every pid is resolved from the event pidfd while live. Overflow, unsupported pidfd reporting, unresolved actor/path, loss, or filesystem event after child exit rejects. The watcher begins before exec and ends after sealed-tree hashing; its start/stop equal fanotify_profile and termination_watch coverage.

The verifier independently parses and cross-checks raw bytes, mount identities, cgroup/PID/FD snapshots, mount_setattr syscall record, and post-remount statx/statvfs while the mount is still held. A signed supervisor summary without these raw observation objects is insufficient. Receipt and evidence limits are fixed at 64 MiB total; individual proc snapshots ≤1 MiB; arrays ≤1,000,000 records subject to the total cap; all records are bounded before allocation.

sealed_tree_manifest is canonical JSON with exact keys {schema,directory_count,file_count,total_size_bytes,directories,files}. schema is core.cfd.f8.r008.sealed_output_tree.v1; JSON has no trailing newline. directories is bytewise path-sorted and each exact row is {path,dev,ino,mode}; every row is a real no-follow directory on the output mount, mode identifies a directory, and paths equal the frozen output inventory's complete directory set. files is bytewise path-sorted and each exact row is {path,size_bytes,dev,ino,nlink,mode,sha256}; nlink is 1, mode is regular-file, size is ≤1 GiB each and ≤16 GiB total, and SHA-256 is recomputed from bytes read through the sealed held FD. Directory paths are unique and cannot collide with file paths; no symlink, device, socket, hardlink, mountpoint, or unlisted path is allowed. directory_count equals array length and is 0..256; file_count equals array length and is 1..2048; total_size_bytes is the exact sum of file sizes. The canonical manifest SHA equals output_seal and output_seal_evidence. The v3 artifacts array must match the files array exactly for path/size/dev/ino/nlink/mode/hash and its output-inventory role. Every file and directory is reopened/checked without following symlinks while the mount remains sealed.

termination_watch remains active through hash_stop; its event list includes only one seal control event after child exit plus pre-exit filesystem events. Watch stop is later than hash stop. output_root's exclusive_writer field is derived from these checks and is not an accepted caller claim. If the task runtime cannot produce and verify every object above, return missing/open with zero credit.

## 4. Locale wrapper ABI and event semantics (replaces v5 §3 generic event rows)

locale_attestation retains the v5 exact top-level schema, but wrapper_events becomes a discriminated union. Every row has exact common keys {sequence,monotonic_ns,tid,call,caller_module_sha256,args,result,errno}. sequence is contiguous; monotonic_ns is positive ≤2^63−1; tid is a registered positive Linux TID ≤2^32−1; caller_module_sha256 is in the pinned runtime closure; errno is exact integer 0..4095; args/result have exact call-specific schemas below; unknown keys/calls reject. Locale names are printable ASCII strings ≤128 bytes, paths are canonical absolute loader paths ≤1024 bytes, symbol/version names ≤256 bytes, flags/masks are exact uint32 values, and handles are exact uint64 IDs.

| call | Exact args | Exact result |
|---|---|---|
| setlocale | {category,locale_arg}; category is a symbolic constant in the pinned glibc locale.h enum, locale_arg is null or ASCII locale name | {return_locale}; null or ASCII locale name |
| newlocale | {category_mask,locale_arg,base_handle_id}; category_mask is uint32, locale_arg ASCII, base handle is null or registered ID | {new_handle_id}; null or new monotonically assigned uint64 ID |
| duplocale | {handle_id}; registered uint64 ID | {new_handle_id}; null or new ID |
| freelocale | {handle_id}; registered, inactive ID | {freed}; exact true |
| uselocale | {handle_id}; null means query; otherwise registered ID | {previous_handle_id,active_lc_numeric}; handle null/ID, locale ASCII |
| pthread_create | {start_routine_module_sha256,attr_is_null}; module hash pinned; attr_is_null is exact true (non-null custom attributes reject) | {child_tid,child_start_ticks}; exact positive IDs registered before application code |
| dlopen | {path,flags}; path is null or canonical absolute path; flags is uint32 | {blocked,handle_id}; policy requires exact true and null |
| dlsym | {handle_ref,symbol,version}; handle_ref is exact {kind,handle_id}, kind is tracked/default/next and ID is null except tracked; symbol is 1..256 ASCII bytes and version is null or 1..256 ASCII bytes | {blocked,found,result_module_sha256}; policy requires exact true, false, null |

locale_t pointer values are never serialized. The wrapper assigns monotonic handle IDs at newlocale/duplocale, records category masks and locale names, marks IDs freed, and resolves each uselocale handle to its LC_NUMERIC value. setlocale category/return values and newlocale/uselocale results are recorded at the ABI boundary. The pinned runtime profile fixes the glibc ABI constants and wrapper build hash. Any untracked locale handle, dlopen/dlsym call (even if blocked), locale other than C, event loss, or thread not registered/probed before application code rejects. The errno field is an observation of the real ABI call where made; blocked loader calls record wrapper decision in result rather than inventing a libc errno.

The trusted supervisor starts the wrappers before executable constructors, records loaded objects from the initial process image, blocks post-start dynamic loading/symbol lookup, and observes every clone/clone3 thread birth; each new thread is stopped until registered and probed. It compares the live /proc task list with the thread registry at each parse/format probe and at exit. Locale probes retain exact v5 fields and have phases definition_parse, argv_option_parse, runparts_numeric_format; lc_all and lc_numeric must equal C. One probe is required immediately before Definition/TMAX parsing and for every source-pinned RealStr call that contributes to RunPARTs. Probe rows have exact keys {sequence,monotonic_ns,tid,phase,lc_all,lc_numeric,callsite_id}; locale strings are exactly C and callsite_id belongs to the pinned source-profile enum. Probe records, ABI event rows, profile/runtime hashes, thread birth/exit table, and signed payload are all exact and bounded. Without this ABI-complete monitor, RealStr text equality is not accepted.

## 5. Publish the complete BI4 grammar; do not cite hash-only schemas

The F8 terminal verifier is the independent bounded Python sidecar decoder, never the DualSPHysics native JBinaryData reader. The native reader rejects foreign host byte order; no cross-endian capability is claimed. This frozen R008 CPU profile accepts only files whose raw header says little-endian and SI64=0 **and** whose producing-process GetByteOrder() observation is LittleEndian. If the producer is big-endian or any file sets SI64=1, this decoder profile returns missing/open; it must not reinterpret by assumption. A future big-endian/SI64 decoder needs a separately versioned and reviewed profile.

For the accepted profile, BI4 grammar is fixed exactly as follows:

1. File is one regular file, link count 1, length 64 bytes..64 MiB. Header is 64 bytes: bytes 0..57 equal ASCII “#FileJBD JPartDataBi4” followed by spaces through offset 57; byte 58 LF; byte 59 NUL; byte 60 is 0; byte 61 is 0; bytes 62..63 are zero. Every integer/floating payload is little-endian because the header and independently observed producer host order both equal little-endian.
2. The file contains exactly one top-level item named JPartDataBi4, with no root arrays and exactly one child item named PART_ followed by exactly four decimal digits; the child has no child items. No trailing bytes or second top-level record.
3. Item marker is length-prefixed UTF-8 string “\nITEM\n”. Item definition fields are length-prefixed name, signed int32 hidden flag, signed int32 hide-values flag, float-format string exactly %.7E, double-format string exactly %.15E, uint32 array count, uint32 child-item count, uint32 values-block byte length. Visibility flags are 0/1. Maximum nodes 2, depth 2, arrays 64, metadata 2 MiB, values per item 128, definition 2 MiB, array definition 4096 bytes, name 128 bytes, string 4096 bytes.
4. A nonempty values block starts with length-prefixed UTF-8 string “\nVALUES”, uint32 value count, then records of length-prefixed name, signed int32 type code and value. Value codes are: 1 UTF-8 text; 2 bool encoded int32 0/1; 3 int8; 4 uint8; 5 int16; 6 uint16; 7 int32; 8 uint32; 9 int64; 10 uint64; 11 float32; 12 float64; 20 int32x3; 21 uint32x3; 22 float32x3; 23 float64x3. No other type code is accepted. Values are unique by sibling name and finite where floating.
5. Each array definition starts with length-prefixed UTF-8 string “\nARRAY”, length-prefixed name, signed int32 hidden flag 0/1, signed int32 type code from 2..12 or 20..23 excluding text code 1, uint32 element count and uint32 byte count. Byte count must exactly equal count times width: 1,2,4,8,12,24 as implied by the listed type. Payload follows immediately. Maximum count is 10,752 per array; aggregate array payload ≤16 MiB; file ends immediately after the final declared child/array/value block. Duplicate sibling value/array/item names reject.
6. The root metadata allowlist and types are fixed by JPartDataBi4.cpp ConfigBasic/ConfigParticles/ConfigCtes/ConfigSimMap/ConfigSimPeri/ConfigSimDiv/ConfigSymmetry/ConfigSplitting: Piece/Npiece uint32; RunCode/Date/AppName/CaseName text; Data2d/NpDynamic/ReuseIds/Symmetry/Splitting bool; Data2dPosY/Dp/H/B/Rhop0/Gamma/MassBound/MassFluid float64; CaseNp/CaseNfixed/CaseNmoving/CaseNfloat/CaseNfluid uint64; CasePosMin/CasePosMax/MapPosMin/MapPosMax/PeriXinc/PeriYinc/PeriZinc float64x3; PeriMode/AxisDiv int32. A profile-specific subset may omit fields not emitted by its pinned writer callsites but may not add a name/type.
7. The PART metadata allowlist/types are Cpart/Npok/Nout/Step uint32; TimeStep/RunTime/timesim float64; DomainMin/DomainMax float64x3; NpTotal/IdMax uint64. Required completion fields are Cpart, TimeStep, Npok, Step; their exact semantics and same-row RunPARTs match remain as in v4.
8. For this frozen CPU single-piece main PART profile, required arrays are Idp uint32, Posd float64x3, Vel float32x3, and Rhop float32, each with count exactly Npok. BoundNor is a separate PartExtra output, not a main PART array; its population is governed by the PartExtra-specific profile and frozen Nbound/UseNormalsFt source contract. Splitting is false for the frozen scope, so Mass/Hvar and all unlisted main-PART arrays reject. A different frozen source/profile must define a new version, not widen this allowlist.

Replace the v5 bi4_format_profile object with this exact structure: {schema,source_revision,writer_source_manifest_sha256,decoder_path,decoder_id,decoder_sha256,producer_byteorder,files}. decoder_path is exactly scripts/f8_r008_safe_bi4_decoder_v1.py; decoder_id is core.cfd.f8.r008.safe_bi4_decode.v1. All hashes are 64 lowercase hex; producer_byteorder is little and must equal producer_byteorder_observation; files is sorted by path and includes every BI4 path in the closed output inventory. Each file row has exact keys {path,role,parse_mode,filecode,si64,writer_callsite_id,root_values,part_values,arrays}. parse_mode is terminal_main_part or opaque_inventory_hash. For terminal_main_part, filecode is exactly JPartDataBi4, si64 is 0, and root_values/part_values/arrays are sorted unique arrays of exact records: root/part value record {name,type_code,required}; array record {name,type_code,required,count_rule}. required is exact JSON bool; type_code is an exact integer from the closed value/array enums above; count_rule is npok for the four required arrays. The full allowed field names/types/count rules are those in items 6–8 above; the terminal row must include the required PART fields/arrays and may contain only source-profile-permitted root metadata. For opaque_inventory_hash, filecode/role/si64/writer_callsite_id still bind to the pinned output inventory and trusted source profile, but the terminal-completion contract makes no semantic claim about its payload: it is bounded-read, identity-checked and SHA-256-bound only. Any such file used by a scientific gate requires that gate's separate semantic scanner. Boundary normals are a separate PartExtra artifact controlled by SvExtraParts and never an array in the terminal main PART; absent PartExtra never implies that the output mode was disabled. Mass/Hvar are forbidden for this frozen non-splitting profile. The source manifest binds JBinaryData/JPartDataBi4 writer sources and decoder_path/decoder_id/decoder_sha256 identify the standalone bounded parser; the full grammar is present in this document and the typed lists, not hidden behind a schema hash. The profile object itself is pinned by the frozen output_inventory dependency and included in the receipt. The existing safe_bi4_decoder_v1 is explicitly little-endian/SI64=0 only; until its exact hash and the above profile are pinned and independently reviewed, BI4 terminal proof remains missing/open. Big-endian support, if ever added, must use a standalone decoder with explicit per-file byte-order dispatch and new synthetic endian fixtures; it cannot be attributed to the official native reader.

## 6. Exact top-level/key sets, verification order, and non-authorization

The top-level exact keys are v3's full set plus output_seal, output_seal_evidence, sealed_tree_manifest, locale_attestation, and bi4_format_profile. The v3 final-artifact clause is narrowed for this contract: final RunPARTs/log/main-PART artifacts are parsed and recomputed; every other required artifact is reopened, bounded-read, identity-checked and hash-verified against the closed inventory, without claiming its semantic format here. All nested keys/enums/bounds derive from v3 plus the explicit v4–v6 replacements; every object has additionalProperties=false; JSON floats and duplicate keys are forbidden. No prose extension creates implementation discretion.

Verification order: task-external policy/root signature and monotone policy sequence; genesis/one fixed registry snapshot and trusted-time nonce; receipt canonical bytes and signature; source/build/output/runtime pins plus actual argv/parser, Definition/control/initial-state and DsphConfig input trace; positive-horizon and terminal in-loop save proof; process tree/reap, locale ABI evidence and actor-aware watch; output_seal_evidence signature and independently rechecked kernel observations; sealed manifest and stable no-follow hashes; narrow BI4 grammar/RunPARTs/log recomputation. Any missing/untrusted/lost/mutable/mismatched fact is missing/open and zero credit.

This contract does not install policy, rotate keys, create a registry, modify any ledger/gate, read production files, or authorize GenCase/native decoder/solver/worker/GPU/queue. F8 remains T1_numerical=false, readiness=false, qualification credit zero until a separate authorization and every frozen scientific gate passes.

## 7. Independent review checklist

1. Is the one-snapshot policy schema and external install/update/anti-rollback boundary coherent?
2. Does one post-exit seal control event coexist consistently with rejecting every post-exit filesystem mutation?
3. Can a verifier independently check all signed raw kernel observations and sealed-manifest cross-links?
4. Are locale ABI argument/result records, locale_t handle mapping and thread birth coverage exhaustive?
5. Does the narrow BI4 profile exactly match the pinned R008 CPU writer/preflight and independent safe decoder without claiming native cross-endian support?
6. Do positive-horizon, DsphConfig, argv/input-trace, fresh-run and zero-credit rules remain unchanged?

Review is read-only. No tests/programs, production HDF5/PART/BI4/bundles, GenCase/native decoder/solver/worker/GPU/queue, or registry/ledger mutation.
