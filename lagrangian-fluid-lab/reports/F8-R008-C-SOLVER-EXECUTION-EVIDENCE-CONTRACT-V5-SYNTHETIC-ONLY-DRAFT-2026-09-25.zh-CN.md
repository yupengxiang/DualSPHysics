# F8 R008 C 阶段 execution-evidence synthetic schema V5（草案）

状态：V5 首轮只读交叉复核为 `REVISE` 后已修订；focused follow-up 确认 query/process 生命周期、terminal guard 与异常/中断 cache 规则在文本层面闭合。当前已实现 synthetic-only journal 的 strict structural parser 与合成测试，但尚无 process/query 因果图、source-callgraph 重算、单槽 cache replay、trusted producer/event source 或 runtime identity 验证。它仍不是 production execution schema，不生成 solver 许可、不关闭 gate、不授予资格信用；有效 parse 也必须输出 `gate_state="open"`、`execution_semantics_verified=false`、T1 false、zero credit。未运行 solver/native/GenCase/worker/GPU/queue。V3/V4 字节、签名 domain、one-shot 收据和历史版本均不得重解释为 V5。

V5 envelope 与 payload schema 固定为 `core.cfd.f8.r008_c_execution_evidence.synthetic.v5`，signature domain separator 固定为 ASCII 字节 `F8-R008-C-EXEC-SYNTHETIC-V5` 后接单个 LF (`0x0a`)；V4 prefix/schema 一律拒绝。source-callgraph ref 的固定 registry target 为 `core.cfd.f8.r008_c_execution_source_callgraph.synthetic.v5`，除本合同明示新增的 process/query closure 字段外，V4 exact source-fragment/AST/driver/instance 规则继承且不得放宽。

## 1. 单一 attempt journal 与全局事件顺序

V4 的独立 query journal 与 process journal 改为一个 descriptor-root referenced `execution_journal`，避免两个日志各自有连续序号但无法证明跨日志先后。V5 evidence payload 使用唯一字段 `execution_journal_binding`（stage=`runtime`, role=`execution_journal`）；固定 registry target schema 为 `core.cfd.f8.r008_c_execution_journal.synthetic.v5`。该 ref 与 `source_callgraph_binding` 使用 V4 继承的 exact descriptor-ref shape `{stage,role,object_id,bytes,sha256}` 及类型/domain/path 规则，不带 caller-selected schema/canonical digest；ref 必须分别匹配固定 `(runtime,execution_journal)` / `(build,source_callgraph)` registry target。旧 `process_journal_binding`、`accinput_query_journal_binding` 及 V4 journal 均不能作为 V5 输入。

journal 顶层 exact keys 为：

```text
{schema,attempt_nonce_hex,source_id,source_binary_sha256,
 coverage_start_ns_hex,coverage_end_ns_hex,event_count,overflow,lost_count,events}
```

本版将 `attempt_nonce_hex` 精确冻结为 32 位小写 hex（128-bit nonce），补足 V2/V4 旧合同仅称“固定长度”但未注明长度的歧义；此格式约束仅用于 V5/V2 synthetic schema，不是 nonce 来源或真实性证明。

V5 structural schema 将 process `exit` 的 `exit_code` 冻结为 exact builtin JSON integer `0..255`，且 `signal=null`；signal 终态则要求 `exit_code=null`、`signal` 为正 builtin integer。V5 单 journal parser 只验证 event nonce 与 journal 顶层 nonce 相等；它尚未接收 evidence payload/V2 attempt 对象，不能声称完成外层 nonce cross-binding。

`schema` 固定如上；nonce/source/binary 必须分别等于同一 evidence payload 的 nonce、runtime-image object id 与 runtime-image raw SHA-256；digest 为 64 位小写 hex。`coverage_start_ns_hex` / `coverage_end_ns_hex` 是 16 位小写 hex binary monotonic nanoseconds，且 start 不晚于 end、每个 event 时间均在闭区间内。可信监测须从 root spawn 前的 invocation 校验覆盖启动边界，并持续覆盖 spawn/exec、全部 solver process/thread 直到 exit/reap；这不表示 exec 先于 spawn。边界覆盖的可信性仍依赖 V5 §4 外部 event-source trust。`overflow` 必须是 builtin `false`，`lost_count` 是 builtin integer `0`（bool 不算 integer）。`event_count == len(events)`，且事件的唯一 `seq` 必须恰为 `0..event_count-1`；`seq`/count 是有界非负 builtin JSON integer（bool 不算 integer）；`mono_ns_hex` 为 16 位小写 hex 且全局非递减（允许相邻事件同一时钟刻度）。全局 `seq` 是唯一事件先后顺序；任何跨事件先后约束都用严格 `seq` 不等式表达，不能要求时钟值严格递增。字节/事件/数组界限沿用 V4 对应的上限。process event 与 loop/poll query event 共用这个 seq 空间，不再通过两份日志各自的 seq 或仅靠同一 attempt nonce 推断因果。

每个 event 都有共同字段 `{seq,mono_ns_hex,kind,attempt_nonce_hex}`；`kind` 只允许 `spawn|fork|clone_process|thread_create|thread_exit|exec|exit|reap|load|cgroup|loop_guard|poll_begin|poll_end`，并必须精确标识对应 branch；每个 event 的 `attempt_nonce_hex` 必须与 journal 顶层及 evidence payload nonce 完全相等。V5 的 process event 各 branch 精确继承 V4 §3 的相应字段并额外要求 `attempt_nonce_hex`，不得省略或增加字段；V5 `loop_guard`/`poll_begin`/`poll_end` 分支的 exact keys 见 §2。`birth_seq_hex` 必须等于创建该 generation 的 `spawn|fork|clone_process` 或 `thread_create` 的全局 `seq` 编成 16 位小写 hex。`spawn` 创建 root generation；root 在首次成功且已核验的 `exec` event 前保持 created，首次 `exec` 转为 running，后续 `exec` 只更新 image binding。`fork|clone_process` 创建 child 并使其在创建 event 上原子进入 running；`thread_create` 同样创建并启动 thread。进程状态由同一个 ordered `events` 序列重算为 `created→running→exited→reaped`，线程状态为 `created→running→thread_exited`；`loop_guard`/`poll_begin`/`poll_end` 只允许出现在 running process generation 上。未知、丢失、重复、跳号、非法状态转移或无法归属于 root 的 event 都使 synthetic outcome 为 `open`。

V5 `control_horizon_audit` exact keys 固定为 `{scope_digest,qualification_row_digest,source_callgraph_binding,execution_journal_binding,entry_count,guard_count,poll_count,poll_end_count,exception_count,all_expected_queries_present,all_polls_terminal,normal_loop_termination_complete,all_active_queries_in_table_domain,zero_active_query,comparison_rule}`；两份 ref 必须与 payload 对应 raw refs 逐字段相等，旧双 journal refs 禁止出现。`scope_digest` 与 `qualification_row_digest` 分别精确等于 payload `scope_binding.sha256` 与 `qualification_row_binding.sha256`（均为 descriptor-ref 原始字节 SHA-256，不是 canonical digest）。`source_callgraph_binding` 指向上述 V5 callgraph schema；`entry_count` 等于该 callgraph 所有 instance `input_count` 之和，guard/poll/poll_end/exception counts 等于 journal 对应 kind/outcome 数；expected-query completeness 从固定 driver→instance→entry topology 与 `intersteps` 重算，并要求每个真实 `condition_result=true` 的 guard 都有调用图所列完整 host-call × input-entry 集合；domain booleans 从冻结时间窗/表轴与 `poll_begin` events 重算。成功语义还要求每个参与本次调用的 driver loop 都有且仅有一个由调用图定义的正常终止 `condition_result=false` guard，且此前 true guards 的 iteration/time-step 转移符合绑定源码；缺少终止 guard、提前退出或无法证明完整 horizon 时 `normal_loop_termination_complete=false`，不得成功。`all_polls_terminal` 精确表示每个 begin 有且仅有一个 matching end（returned 或 exception 都算 terminal）；exception end、无 end 均禁止 execution success，且 exception count 必须为零。所有 boolean/count 均须 builtin 类型（bool 不可作 integer），且由 parser 重算；`comparison_rule` 固定为 `binary64_numeric_strict_no_tolerance`。

## 2. invocation 必须绑定 solver root 与 query 事件生命周期

V5 `invocation` exact object 新增并要求 `process_generation_id`，同时保留 V4 exact argv、cwd、环境、case/restart、executable/runtime binding。该 generation 必须由本 attempt 唯一 root `spawn` event 创建；该 spawn 的 supervisor identity binding、PID namespace/TGID、kernel start time 与 invocation 完全一致。root 首次 `exec` 的 executable object/raw SHA、`argv_sha256`、cwd object id、environment SHA 必须与 invocation 与已固定 runtime-image binding 相等；root 上的 loop/query event 只能在此匹配 exec 后出现。solver root 及其可接受 solver 子进程只能沿 journal 的 `fork/clone_process` 有向边到达；child generation 创建时继承 parent 当刻 image/code binding，每次后续 exec 都必须通过同一 solver image allowlist；child query 还必须在其 image 状态已按该规则闭合后发生。任何 query process 均须是该 root 或该 root 下登记、image allowlist 匹配的 solver child，不接受 supervisor、decoder、其他同 attempt process 或 orphan generation 的 query。

每个 `loop_guard` 与 `poll_begin` 必须满足 `creation_seq < event.seq < exit_seq`，且其 process 的当时 image binding 在 solver allowlist 中；禁止首次匹配 `exec` 之前的 root query，也禁止后续 exec 切换到非 solver image 后继续记录 query。`poll_begin` 的单调时间戳依全局 seq 非递减；允许创建/query/退出落在相同 clock tick。退出后的事件、reaped 后事件、未 spawn 的 child 事件均拒绝。每条 `poll_begin.guard_seq` 必须严格小于其 `seq` 并指向同一 generation、同一 driver loop iteration 的 guard；poll 时间戳 bit-exact 等于 guard 的 `time_step`，且 guard 的 `condition_result=true`。`poll_begin` 必须在调用 `GetAccValues` 前同步记录，唯一标识实际 host call；调用返回或抛出时各追加恰一个 `poll_end`，其 `poll_begin_id` 指向同一 generation 的 begin。end 必须早于该 generation 的任何后续 `exec`/`exit`，并仍绑定 begin 时的 solver image。若 timeout/signal/process exit 打断调用，则允许缺少 end，但该 attempt 必须保持 incomplete/nonpassing；不得把它计为 terminal/success。`poll_end` outcome 仅 `{returned,exception}`；任何 exception outcome 都令该 attempt execution semantics fail/open，即使后续进程成功清理。guard 必须来自调用图所列实际 CPU/GPU/VRes driver 路径。`poll_begin` 必须一一对应 `RunCpu/RunGpu` 对每个 `Inputs[c]` 实际调用的 `GetAccValues`，包括当前 `TimeIni/TimeEnd` 窗外的 inactive entry，因为它们也会更新 `LastTimestepInput` cache；`active` 由冻结时间窗重算，不采信 caller boolean。为保留 V4 callgraph 的确切语义（特别是一个 VRes driver guard 可服务其有序多个 solver instance），V5 branch exact keys 为：`loop_guard={seq,mono_ns_hex,kind,attempt_nonce_hex,process_generation_id,driver_id,loop_iteration_id,time_step_ieee754_hex,time_max_ieee754_hex,condition_result}`；`poll_begin={seq,mono_ns_hex,kind,attempt_nonce_hex,poll_begin_id,process_generation_id,solver_instance_id,driver_id,guard_seq,callsite_id,integrator,interstep,input_entry_index,timestep_ieee754_hex,active,cache_action,cache_source_seq,table_raw_binding}`；`poll_end={seq,mono_ns_hex,kind,attempt_nonce_hex,poll_begin_id,process_generation_id,outcome}`。`poll_begin_id` 精确等于该 begin event 的 `seq`，end 内对应的 `poll_begin_id` 是被引用的 begin seq；`callsite_id`、`integrator`、`interstep` 的 enum/ASCII 规则继承 V4；`loop_iteration_id` 与所有 sequence/index 按 V4 的有界 builtin JSON integer 规则校验（bool 不是 integer）。`active` 与 table/cache provenance 规则继承 V4 §3，且所有 inactive begin 仍参与 cache replay。用不同进程记录 query、跨 attempt 复用 journal 或只把 process id 加入 allowlist 均无效。

## 3. `LastTimestepInput` cache 的可复算单槽状态机

异常后的缓存状态必须按 C++ 的写入顺序处理：`GetAccValues()` 先写 `LastTimestepInput`，再读取并逐步填充 `LastOutput`。若该次 miss 的 `poll_end.outcome="exception"`，时间戳槽已被占用但输出是否完整未知；该异常 poll 不得作为有效 cache source。其后同 instance、数值相等的 timestep 会按源码命中该槽，但返回值无法证明，必须记为 unverified 并令 attempt 保持 open；只有随后不同 timestep 的 miss 才能重建有效 cache source。exception 后如出现同时间 hit，parser 不得用此前成功 miss 回填或把它接受为普通 cache hit。该规则影响诊断重放，不改变任何异常 attempt 均 nonpassing 的结论。

按当前 `GetAccValues()` 分支，inactive 和 cache-hit 在表读取前返回，只有 active miss 会进入 Ace/Vel 表读取；因此若它们被记录为 exception，说明调用图/事件分类与绑定源码不一致，必须 unresolved/open，不能当作一般性 terminal failure。

没有 matching `poll_end` 的 `poll_begin`（包括 signal、timeout 或监测中断）对 cache replay 也按 output-unknown 处理：调用已先更新该 instance 的 timestep 槽，但不能证明 `LastOutput` 完整。若 journal 随后还出现同一 instance 的同时间 poll，它不得把这个悬空 begin 当作有效 cache source；不同 timestep 的新 miss 可以重建局部可重放状态，但 attempt 仍永久 nonpassing/open。不存在后续 poll 时仍须把悬空 begin 保留在失败分母，禁止当作 returned 或成功 terminal。

源码中 cache 是每个 `JDsAccInputMk` 对象上的单个 `LastTimestepInput`/`LastOutput`（`src/source/JDsAccInput.h`、`JDsAccInput.cpp::Reset/GetAccValues`），不是无界的 `(time→result)` 字典。V5 callgraph 固定每个 solver process generation 内 `JDsAccInput` wrapper 与其有序 `Inputs[c]` 到 `JDsAccInputMk` instance 的唯一映射。当前源码的 `Reset()` 在构造时初始化 `LastTimestepInput=-1`、析构时释放该 instance；R008 V5 合同假设每个 callgraph 登记的 instance 在首次 driver loop 前完成唯一构造，运行期间不重建/重置，销毁不晚于所属 process generation 退出。若 source/build-bound callgraph 不能证明此生命周期，或 future source 出现未进入 journal/callgraph 的 runtime reset/reconstruction，则 cache 语义必须 unresolved/open。每个 `poll_begin` 精确带 `{driver_id,solver_instance_id,input_entry_index,cache_action,cache_source_seq}`；`cache_action` 仅 `miss|hit`，miss 的 `cache_source_seq=null`，hit 必须引用同一 instance 最近一次仍为当前 cache 值的 miss。`table_raw_binding` 复用 V4 provenance 规则：inactive begin 必须为 null；active miss 必须精确绑定本 entry；active hit 必须同时匹配本 entry 与当前 cache-source miss 的 table binding。

验证器按全局 event seq 对每个 callgraph instance 的首次 `poll_begin` 以 `LastTimestepInput=-1` 开始并重放唯一状态；每个 finite binary64 begin 都先与源代码 guard `LastTimestepInput>=0 && timestep==LastTimestepInput` 比较；仅该条件为真时是 `hit` 并复用当前 cache source 的 `LastOutput`，否则是 `miss` 并将当前 timestep/source 替换为 cache。`+0` 与 `-0` 因源代码数值 `==` 而相等，不按 hex bits 比较；负值依源 guard 强制 miss；NaN/Infinity 禁止；禁止 epsilon。任一 intervening miss、generation 改变或不同时间 poll 后引用陈旧 miss 一律拒绝；若审计范围发现可在 solver loop 期间发生 Reset/reconstruction，则因 V5 未为其定义 runtime event 而只能 unresolved/open。每个 begin 的唯一 end outcome 必须可追溯；`exception`、无 end、重复/孤立 end 均使该 attempt nonpassing/open，并将已开始查询保留在 case/attempt denominator 中。poll 序列还必须匹配 callsite/integrator/interstep 的源码调用顺序；同一 guard 下的 Symplectic predictor/corrector 两次 host call 不可合并为一条 poll。

同时以已绑定的 source-callgraph 重算 loop guard、active-window、table-domain 和 poll 序列。空 journal、零 active poll、缺少一个应有 poll、query 在进程退出后出现或 cache 记录与单槽重算不一致，只能生成明确失败/未证明诊断：`gate_state="open"`、`execution_semantics_verified=false`、`qualification_credit=0`。

- `test_c_execution_synthetic.py::test_query_from_unrelated_process_generation_is_rejected`
- `test_c_execution_synthetic.py::test_query_after_solver_generation_exit_is_rejected`
- `test_c_execution_synthetic.py::test_invocation_must_match_unique_solver_root_spawn_and_exec`
- `test_c_execution_synthetic.py::test_cache_hit_must_reference_current_single_slot_miss`
- `test_c_execution_synthetic.py::test_cache_revisit_after_intervening_time_is_a_miss`
- `test_c_execution_synthetic.py::test_exception_after_cache_update_never_becomes_pass`
- `test_c_execution_synthetic.py::test_interrupted_poll_without_terminal_event_is_incomplete`
- `test_c_execution_synthetic.py::test_missing_query_event_or_overflow_keeps_attempt_open`

每项从 V5 synthetic public parser 验证拒绝/诊断；不调用 V4/V5 producer、正式 C attempt 或任何 solver/native/worker/GPU/queue。即使所有负测通过，也只证明 parser 对合成对象图按合同 fail closed。

## 4. 不变的生产信任边界

V5 的合并序号可以证明所提交 journal 内部的顺序，不能证明 trusted supervisor 观察完整、没有漏报，不能证明 supervisor 没有伪造，也不能认证文件来自实际加载的 binary。signature/key activation、revocation、event-source trust、build/source-to-loaded-code closure、cgroup resource-event producer 与 runtime attestation 仍未解决；这些前提未有独立 root capability 时，production C gate 必须保持 disabled。V5 不允许将 caller-supplied event JSON、schema tag、content hash 或 parser PASS 升级为 solver execution evidence 或 T1。
